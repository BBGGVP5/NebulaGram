# Архитектура NebulaGram

## Почему не Kotlin Multiplatform

Официальные клиенты Telegram написаны на разных языках и собираются разными
системами:

| Клиент | Язык | Сборка |
|---|---|---|
| Android (`DrKLO/Telegram`) | Java + C++ (tgnet, ffmpeg, voip) | Gradle + NDK |
| iOS (`TelegramMessenger/Telegram-iOS`) | Swift + Obj-C | Bazel |
| Desktop (`telegramdesktop/tdesktop`) | C++ / Qt | CMake |

Общего UI-кода между ними нет и быть не может: KMP пришлось бы переписать
клиент с нуля. Поэтому шарится не UI, а **ядро туннеля** — и оно на Go, потому
что и Xray-core, и sing-box написаны на Go. Один Go-модуль даёт:

* `nebulalink.aar` — Android (gomobile);
* `NebulaLink.xcframework` — iOS (gomobile);
* `libnebulalink.{dll,so,dylib}` — desktop (`-buildmode=c-shared`).

## Слои

```
┌──────────────────────────────────────────────────────────┐
│  Клиенты (форки Telegram)                                │
│  Android: Material 3     iOS: Liquid Glass    Desktop: Qt│
│  — рендерят декларативное меню из settings.Menu()        │
└───────────────┬──────────────────────────────────────────┘
                │ одна функция: Call(method, payloadJSON) -> JSON
┌───────────────▼──────────────────────────────────────────┐
│  core/api — JSON-фасад                                   │
├──────────────────────────────────────────────────────────┤
│ store      состояние (серверы, подписки, настройки)      │
│ settings   типы настроек + СХЕМА МЕНЮ для всех платформ  │
│ remnawave  подписки, HWID-заголовки, профиль-хедеры      │
│ link       vless/vmess/trojan/ss/hysteria2/tuic          │
│ xraycfg    сборка/разбор конфигов Xray                   │
│ singboxcfg сборка/разбор конфигов sing-box               │
│ probe      TCP- и URL-замеры (свой SOCKS5-диалер)        │
│ tunnel     жизненный цикл, реестр ядер                   │
└───────────────┬──────────────────────────────────────────┘
                │ интерфейс tunnel.Instance
┌───────────────▼──────────────────────────────────────────┐
│  runtime/xray, runtime/singbox — обёртки над ядрами      │
└──────────────────────────────────────────────────────────┘
```

### Почему фасад — JSON, а не типизированный API

Биндингов три (gomobile для Android, gomobile для iOS, cgo для десктопа).
Типизированный API пришлось бы расширять в трёх местах при каждой новой опции.
С фасадом граница — две строки, а новая функция появляется добавлением метода в
`handlers`. Клиент старой версии на новом ядре получит понятную ошибку
`unknown method`, а не падение при линковке.

### Почему ядра туннеля не залинкованы в `core`

Xray-core и sing-box — тяжёлые зависимости с меняющимся между релизами API.
Они спрятаны за `tunnel.Instance` и регистрируются на старте
(`tunnel.Register`). Обновление Xray затрагивает один файл в `runtime/xray` —
ни `core`, ни клиенты не пересобираются логически.

Репозиторий поэтому разбит на четыре Go-модуля:

| Модуль | Зависимости | Зачем |
|---|---|---|
| `core/` | только stdlib | вся логика; тесты идут за секунды |
| `runtime/xray/` | xray-core | обёртка над Xray |
| `runtime/singbox/` | sing-box | обёртка над sing-box (в работе) |
| `bind/` | core + runtime/* | gomobile и C-ABI, здесь ядра линкуются |

Локально они связаны через `go.work` и `replace`, поэтому репозиторий
самодостаточен и ничего не нужно публиковать в модуль-прокси.

## Свой конфиг у каждого сервера

Подписка не обязана отдавать ссылки. Remnawave умеет отдавать `v2ray-json` —
массив полноценных конфигов Xray, по одному на сервер, — и `singbox`, где один
документ описывает сразу все серверы. В таких конфигах есть маршрутизация,
DNS, фрагментация и прочее, чего в ссылке нет.

NebulaLink сохраняет такой документ **целиком** и запускает как написано:

* поля сервера (адрес, протокол, задержка) нужны только для списка и пинга;
* при подключении к документу пришивается наш локальный inbound, а проксирующий
  outbound переименовывается в `proxy`, чтобы счётчики трафика его нашли;
  ссылки на старый тег в правилах маршрутизации переписываются автоматически;
* для sing-box вместо этого выставляется `route.final` на тег нужного сервера;
* всё остальное, что написал провайдер, остаётся нетронутым.

То же самое работает, если пользователь вставит свой конфиг руками — он
становится сервером с протоколом `custom`.

### Как это не превращается в мегабайты

Живая панель на 81 сервер отдаёт 0.6 МБ шаблонов в формате `v2ray-json` и
2.7 МБ в `singbox` (там документ у всех одинаковый). Поэтому:

* документы не лежат внутри записей серверов — они складываются в пул,
  адресуемый по хешу содержимого, и сжимаются gzip;
* одинаковые документы хранятся один раз;
* в клиент шаблоны не уходят **никогда** — `model.ForClient` вырезает их из
  ответов, потому что UI работает только с идентификатором сервера.

Замеры на той же панели: файл состояния 232 КБ (`v2ray-json`) и 54 КБ
(`singbox`), страница списка серверов для UI — 22 КБ.

## Режимы туннеля

**Proxy (по умолчанию).** Ядро поднимает SOCKS5 на `127.0.0.1:10808`, клиент
сам ходит через него. Telegram уже умеет SOCKS5 — на Android это
`SharedConfig.ProxyInfo`, на десктопе `MTP::ProxyData`, на iOS штатные настройки
прокси. Значит **в сетевой стек Telegram мы не патчим ничего**. Плюс: на iOS не
нужен entitlement NetworkExtension, сборка ставится через sideload.

**VPN (опция).** Android — `VpnService` + tun2socks; desktop — TUN через
привилегированный хелпер; iOS — `NEPacketTunnelProvider`, только при платном
Apple-аккаунте. Ядро отдаёт тот же конфиг, меняется только точка входа трафика.

Звонки: в proxy-режиме включается штатная опция Telegram «использовать прокси
для звонков», медиа идёт через ваш сервер без сторонних релеев.

## Идентификация устройства (HWID)

Remnawave умеет ограничивать число устройств. Ядро шлёт заголовки
`x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model`. HWID генерируется при
первом запуске (16 hex-символов), хранится в `nebulalink.json` и меняется
пользователем вручную или кнопкой сброса.

## Единое меню на трёх платформах

`settings.Menu()` возвращает описание экранов: секции, строки, типы виджетов,
ключи локализации, команды. Каждый клиент рендерит это своими нативными
средствами — Material 3 на Android, Liquid Glass на iOS, Qt на десктопе.
Новая опция добавляется один раз в Go, и появляется везде. Тест
`TestMenuIsRenderable` проверяет, что каждая команда меню существует в ядре,
поэтому «мёртвых» пунктов в UI не бывает.

## Состояние

Всё состояние — один JSON-файл `nebulalink.json` в приватной директории
приложения, запись атомарная (temp + rename). Битый файл не удаляется, а
переименовывается в `.corrupt`, чтобы пользователь мог достать оттуда ссылки.
